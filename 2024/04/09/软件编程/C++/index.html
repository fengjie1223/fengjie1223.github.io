    C++核心技术实操文档

    描述：本文档聚焦C++核心实用技术，详细梳理23种设计模式、C++泛编程（自动类型推导、函数模板、类模板）及INI文件读写的核心用法，包含具体代码示例、API说明及注意事项，适配实际开发场景，助力开发者快速掌握相关技术并应用于项目开发。文档内容经过校验，删减冗余错误，补充实操细节，兼顾规范性与实用性。

    一、23种设计模式

    参考链接：https://mp.weixin.qq.com/s/g5rL3ZhghB8zpdQqVuZIBQ（该链接包含设计模式详细原理及完整示例，可结合本文档基础内容拓展学习）

    1.1 设计模式简介

    设计模式是软件开发中，针对常见问题总结的可复用解决方案，旨在提高代码的可读性、可维护性、可扩展性和复用性，降低模块间耦合度，使代码更易迭代和维护。23种设计模式按功能分为三大类：创建型模式、结构型模式和行为型模式，各类模式的核心定位及包含的具体模式如下，明确各类模式的适用场景，便于实际开发中快速选型。

    1.1.1 创建型模式

    核心作用：负责对象的创建，隐藏对象创建的细节（如构造函数、实例化逻辑），降低代码间的耦合度，使代码更具灵活性，便于后续对象创建逻辑的修改和扩展。包含以下4种模式：

    • 工厂&抽象工厂模式：工厂模式用于创建单一类型对象，抽象工厂模式用于创建一组相关联的对象，适用于对象类型较多、创建逻辑复杂的场景。

    • 生成器模式：将对象的构建与表示分离，分步构建复杂对象，适用于对象属性较多、构建过程繁琐的场景（如构建一个包含多个配置项的对象）。

    • 原型模式：通过复制现有对象（原型）创建新对象，无需重新执行构造逻辑，适用于对象创建成本高、需快速实例化的场景。

    • 单例模式：确保一个类只有一个实例，并提供一个全局访问点，适用于全局配置、工具类等场景（如日志工具、配置管理）。

    1.1.2 结构型模式

    核心作用：负责类和对象的组合，通过合理的结构组合，实现新的功能，同时保持类和对象的独立性，便于单个类/对象的修改和复用。包含以下7种模式：

    • 适配器模式：将一个类的接口转换成客户端期望的另一个接口，解决类之间的接口不兼容问题，适用于已有类接口无法修改但需适配新场景的情况。

    • 桥接模式：将抽象部分与实现部分分离，使两者可以独立变化，适用于抽象和实现均可能发生变化的场景，降低两者的耦合度。

    • 组合模式：将对象组合成树形结构，用于表示“部分-整体”的层次关系，客户端可统一处理单个对象和组合对象，适用于树形结构场景（如文件夹与文件）。

    • 装饰模式：动态给对象添加额外功能，无需修改原有类，适用于需灵活扩展对象功能、且不希望通过继承实现的场景。

    • 外观模式：为多个复杂的子系统提供一个统一的入口，简化客户端与子系统的交互，适用于子系统较多、交互复杂的大型项目。

    • 享元模式：复用相同或相似的对象，减少对象创建数量，降低内存消耗，适用于对象数量多、属性重复度高的场景（如文本编辑器中的字符）。

    • 代理模式：为其他对象提供一个代理，控制对原对象的访问，适用于需添加访问控制、日志记录、缓存等增强逻辑的场景。

    1.1.3 行为型模式

    核心作用：负责对象间的通信和行为分配，定义对象间的交互规则，使对象行为更具灵活性和可扩展性，便于协调多个对象的行为。包含以下12种模式：

    • 责任链模式：将请求的处理者连成一条链，请求依次传递，直到有一个处理者处理该请求，适用于请求需多个对象依次处理的场景（如权限校验）。

    • 命令模式：将请求封装成对象，使请求的发送者与接收者分离，便于请求的存储、复用和撤销，适用于请求需异步处理、批量处理的场景。

    • 迭代器模式：提供一种方法遍历聚合对象中的元素，无需暴露聚合对象的内部结构，适用于需统一遍历不同类型聚合对象的场景（如遍历数组、链表）。

    • 中介者模式：定义一个中介者对象，协调多个对象之间的交互，减少对象间的直接耦合，适用于对象间交互频繁、关系复杂的场景。

    • 备忘录模式：保存对象的内部状态，以便后续可以恢复到该状态，适用于需支持撤销、回滚操作的场景（如编辑器的撤销功能）。

    • 观察者模式：定义对象间的一对多依赖关系，当一个对象状态发生变化时，其所有依赖对象都会收到通知并自动更新，适用于事件监听、消息通知等场景。

    • 状态模式：允许对象在内部状态发生变化时改变其行为，使对象看起来好像修改了它的类，适用于对象状态较多、状态切换逻辑复杂的场景。

    • 策略模式：定义一系列算法，将每个算法封装起来，并使它们可以相互替换，使算法的变化独立于使用算法的客户，适用于多种算法可选、需灵活切换的场景。

    • 模板方法模式：定义一个算法的骨架，将一些步骤延迟到子类中实现，子类可在不改变算法骨架的情况下重定义算法的某些步骤，适用于算法流程固定、部分步骤需定制化的场景。

    • 访问者模式：定义一个用于访问对象结构中各个元素的接口，使不同的访问者可以对同一元素执行不同的操作，适用于对象结构稳定但需频繁添加新操作的场景。

    1.2 常用设计模式（重点实操）

    在实际C++开发中，并非所有设计模式都会频繁使用，以下3种模式应用场景最广泛，是必备掌握的核心模式，补充核心实现思路，便于快速上手实操：

    1. 单例模式：确保一个类只有一个实例，并提供一个全局访问点。核心实现：私有化构造函数、拷贝构造函数和赋值运算符，提供一个静态成员函数返回唯一实例。适用于全局配置、工具类等场景（如日志工具、配置管理）。

    2. 观察者模式：定义对象间的一对多依赖关系，当一个对象状态发生变化时，其所有依赖对象都会收到通知并自动更新。核心实现：定义被观察者（主题）和观察者接口，被观察者维护观察者列表，状态变化时遍历通知所有观察者。适用于事件监听、消息通知等场景（如UI界面更新、状态同步）。

    3. 策略模式：定义一系列算法，将每个算法封装起来，并使它们可以相互替换，使算法的变化独立于使用算法的客户。核心实现：定义算法接口，不同算法实现该接口，客户端通过调用接口实现算法切换。适用于多种算法可选、需灵活切换的场景（如排序算法、支付方式选择）。

    二、C++泛编程

    C++泛编程（泛型编程）是一种基于模板的编程思想，核心是“算法与数据结构分离”，通过模板将数据类型参数化，实现代码的复用，使同一套代码能够适配多种数据类型，提高代码的通用性和灵活性，降低冗余，同时保证代码的类型安全性（编译阶段校验类型）。以下梳理泛编程中最常用的核心知识点：自动类型推导、函数模板、类模板，补充实操细节和常见问题解决方法。

    2.1 自动类型推导（auto关键字）

    auto关键字是C++11及以上版本引入的自动类型推导工具，能够根据变量的初始化值，自动推导变量的具体类型，无需手动声明类型，简化代码编写（尤其适用于复杂类型），但需遵循严格的使用规范，避免滥用导致代码可读性下降、维护困难。

    2.1.1 核心使用规则（补充细节，规避错误）

    • auto可以自动推导变量类型，可省略手动声明类型，但不能省略变量名，且变量必须初始化（否则编译器无法推导类型，直接报错）；初始化值的类型必须明确，不能是未定义的表达式。

    • 不要滥用auto关键字：对于简单类型（如int、float、string、bool），手动声明类型更易读，降低他人维护成本；auto适用于复杂类型（如迭代器、函数指针、lambda表达式返回值），可简化代码。

    • 不要用auto作为函数形参：C++标准不支持auto作为函数形参（无法在编译阶段确定形参类型，导致函数无法实例化），若需适配多种类型的形参，应使用函数模板，而非auto。

    • 推荐用auto作为函数指针的类型声明：简化复杂函数指针的声明语法（如指向多参数、复杂返回值的函数指针），提高代码可读性和简洁度。

    • 补充规则：auto推导时会忽略顶层const（如const int a = 10; auto b = a; 推导b为int，而非const int），若需保留const，需显式声明为const auto；auto无法推导数组类型，会将数组推导为指针类型。

    2.2 函数模板

    函数模板是泛编程的核心工具之一，用于定义可适配多种数据类型的通用函数。通过模板参数，将函数中的数据类型参数化，使同一套函数逻辑能够处理不同类型的数据（如int、float、string等），无需重复编写多个重载函数，提高代码复用性，同时便于后续逻辑的统一修改和维护。

    • 若模板函数逻辑不适用于某类数据类型（如自定义类未重载加法运算符、参数类型不支持函数内部逻辑），则无法调用该模板函数，会编译报错；解决方法：要么给自定义类重载对应的运算符，要么特化模板（为该类型单独实现模板函数）。

    2.3 类模板

    类模板与函数模板原理类似，用于定义可适配多种数据类型的通用类。通过模板参数，将类中的成员变量、成员函数的类型参数化，使同一套类逻辑能够处理不同类型的数据，适用于实现通用的数据结构（如链表、栈、队列、容器等），提高代码复用性，避免为每种数据类型重复编写相似的类。

    2.3.3 核心注意事项（补充实例化和编译细节）

    • 类模板实例化时，必须显式指定模板参数类型，例如Container、Container，编译器无法自动推导类模板的参数类型（与函数模板不同）；若模板参数指定了默认类型，可省略模板参数，如template class Container;，实例化时可直接写Container c(100)。

    • 类模板的成员函数可以在类内定义，也可以在类外定义；类外定义时，需重新声明模板参数，且类名后必须指定模板参数（如ClassName::add_member），否则编译器无法关联模板类和成员函数。

    • 类模板可用于实现通用数据结构，避免为每种数据类型重复编写相似的类，提高代码复用性（如C++标准库中的vector、list、map等，均为类模板实现）；自定义类模板时，需确保逻辑适用于所有可能的模板参数类型，或通过特化模板适配特殊类型。

    • 补充：类模板的特化（针对特定类型单独实现类模板），适用于某类数据类型无法适配通用逻辑的场景，例如为string类型特化Container类，修改print_data的输出格式；类模板不能单独编译，需将模板定义和类外成员函数实现放在头文件中，避免链接错误。

    三、INI文件读写

    INI文件是一种简单的配置文件格式，以键值对（key=value）的形式存储配置信息，结构清晰、易于编写和读取，无需复杂的解析逻辑，广泛应用于C++项目的配置管理（如端口配置、路径配置、参数设置、数据库连接信息等）。C++中无内置的INI读写工具，需借助第三方库实现，本文档梳理常用的INI读写库，重点讲解inicpp库的实操用法（含代码示例、API说明、常见问题解决）及注意事项，删减冗余错误，补充实操细节。

    3.1 常用INI读写库对比（补充优缺点和选型建议）

    C++中无内置的INI读写工具，需借助第三方库实现，以下是5种常用库的功能对比、优缺点及适用场景，方便根据项目需求快速选型，避免选型不当导致的开发效率低下：

    • inih：轻量级库（代码量少，仅需包含1-2个头文件），仅支持读取INI参数，支持注释解析（#、;开头的注释）；不支持写入参数。需通过C语言结构体管理配置数据，适配C和C++项目，适用于仅需读取配置、对代码体积要求高（如嵌入式C++项目）的场景。

    • inicpp：功能完善，支持读取、写入INI参数，支持注释解析和添加；注释需为单独一行（不可与参数同列），否则写入时会删除同列注释。适配C++11及以上版本，纯C++编写，易用性高，API简洁，推荐优先使用；若包含hpp文件后编译报错，需在该文件中添加头文件#include （解决部分编译器兼容问题）。

    • QSettings：Qt框架自带库，无需额外引入第三方库，支持读取、写入INI参数，支持注释解析；缺点是写入参数时，会自动删除原有注释（无法保留注释），且仅适用于Qt项目，适用于Qt项目中无需保留注释、快速实现INI读写的场景。

    • SimpleIni：功能稳定，支持读取、写入INI参数，支持注释解析；缺点是写入参数时会删除原有注释，且与OpenCV的ACCESS_MASK存在命名冲突（解决方法见3.2），适配Windows和Linux平台，适用于非OpenCV、无需保留注释的C++项目。

    • IniParser：支持读取、写入INI参数，支持注释解析；写入参数时会删除原有注释，对Linux系统兼容性更好（Windows平台需轻微修改配置），API略繁琐，适用于Linux平台下的C++项目，且无需保留注释的场景。

    补充选型建议：非Qt项目、需保留注释、兼顾读写功能 → 选inicpp；Qt项目、无需保留注释 → 选QSettings；仅需读取、代码体积敏感 → 选inih；Linux平台优先 → 选IniParser；非OpenCV项目、无需保留注释 → 选SimpleIni。

    3.2 SimpleIni库冲突解决（补充细节，避免错误）

    SimpleIni库与OpenCV的ACCESS_MASK存在命名冲突（两者均定义了ACCESS_MASK宏），导致同时引用两个库时编译报错，两种解决方法如下（优先推荐方法1，避免修改头文件顺序导致的其他冲突）：

    1. 不使用命名空间：避免使用using namespace cv; 和using namespace SimpleIni;，通过指定命名空间（如cv::、SimpleIni::）调用相关接口，彻底避免宏定义冲突，示例：cv::imread(“img.jpg”); SimpleIni::CSimpleIniA ini;。

    2. 调整头文件引用顺序：先引用SimpleIni.h，再通过#undef ACCESS_MASK解除冲突，最后引用OpenCV相关头文件，示例如下（注意：该方法需严格遵循引用顺序，否则冲突无法解决）：
      `#include “SimpleIni.h” // 先引用SimpleIni头文件

    #undef ACCESS_MASK // 解除与OpenCV的命名冲突（注销SimpleIni定义的ACCESS_MASK）
    #include <opencv2/opencv.hpp> // 再引用OpenCV相关头文件
    using namespace cv; // 此时可正常使用cv命名空间，无冲突
    `

    3.3.2 核心API说明（补充参数细节和异常场景）

    inicpp库的核心操作围绕IniManager类展开，以下是常用API的详细说明，涵盖实例化、写入、读取三大核心操作，补充参数细节、异常场景及注意事项，避免实操报错：

    1. 实例化（创建INI管理对象）

    核心功能：创建IniManager对象，关联INI文件（若文件不存在，后续写入操作会自动创建该文件；若文件路径不可访问，会抛出异常），支持普通实例化和指针实例化，Qt项目中需注意路径编码转换（避免中文路径乱码）。

    • 普通实例化（非Qt项目）：
      `// 传入INI文件路径（相对路径/绝对路径），相对路径相对于可执行文件所在目录

    inicpp::IniManager _ini(“config.ini”);
    // 补充：绝对路径示例（Windows）：inicpp::IniManager _ini(“D:/project/config.ini”);
    // 补充：绝对路径示例（Linux）：inicpp::IniManager _ini(“/home/project/config.ini”);`

    • 指针实例化（Qt项目，需转换路径编码，避免中文乱码）：
      `#include

    #include

    QString inistr = “参数管理/复卷检测.ini”; // Qt中的路径（支持中文路径）
    // 实例化指针，将QString路径转换为std::string（适配inicpp库，toLocal8Bit解决中文乱码）
    inicpp::IniManager *_ini = new inicpp::IniManager(inistr.toLocal8Bit().toStdString());

    // 补充：使用完指针后，需手动释放内存，避免内存泄漏
    // delete _ini;
    // _ini = nullptr;
    `

    2. 写入参数（modify/modifyComment）

    核心功能：写入、修改INI文件中的键值对和注释，无对应段/键时会自动创建，写入操作会自动保存到文件，具体用法如下，补充参数限制和异常说明：

    • 仅修改/添加键值对：
      `// 参数1：段名（string类型，支持中文）；参数2：键名（string类型，支持中文）；参数3：值（string类型，支持中文）

    // 无段/键时自动创建，有则覆盖原有值
    _ini.modify(“段名”, “键名”, “值”);
    // 示例：_ini.modify(“rtsp”, “port”, “554”);`

    • 修改/添加键值对并添加注释：
      `// 参数4：注释（string类型，支持中文），注释会单独成行，不可与键值同列

    _ini.modify(“段名”, “键名”, “值”, “注释内容”);
    // 示例：_ini.modify(“rtsp”, “port”, “554”, “rtsp监听端口”);`

    • 仅修改注释（不改变键值）：
      `// 参数3：新注释内容（string类型），仅更新注释，键值保持不变；无注释时自动创建

    _ini.modifyComment(“段名”, “键名”, “新注释内容”);
    // 示例：_ini.modifyComment(“rtsp”, “port”, “rtsp监听端口，默认554”);`

    补充：写入时，若键值对或注释包含特殊字符（如=、#、;），会导致解析异常，需对特殊字符进行转义（如将=转义为=）。

    3. 读取参数（直接读取/类型转换）

    核心功能：读取INI文件中的键值对，默认返回string类型，支持转换为int、double等基础类型，Qt项目中需转换为QString使用；读取不存在的段/键时，会抛出异常，建议先通过isKeyExist判断是否存在。

    • 直接读取（返回string类型）：
      `// 格式：_ini[“段名”][“键名”]，返回值为string类型

    std::string 键值 = _ini[“段名”][“键名”];
    // 示例：std::string port = _ini[“rtsp”][“port”];`

    • Qt项目中读取（转换为QString，避免中文乱码）：
      `#include

    #include

    // 方式1：普通读取转换（适用于普通实例化）
    QString port = QString::fromLocal8Bit(_ini[“rtsp”][“port”].c_str());
    // fromLocal8Bit解决中文乱码，适配Windows和Linux

    // 方式2：指针实例化读取（Qt项目常用）
    QString str_key = “rtsp”;
    QString ip = QString::fromLocal8Bit((*_ini)[str_key.toLocal8Bit().toStdString()][“IP”].c_str());
    qDebug() << “PLC1:IP:” << ip;`

    • 类型转换（string转int/double）：
      `// string转int：若值无法转换为int（如非数字字符串），返回0

    int 键值_int = _ini[“段名”].toInt(“键名”);
    // 示例：int port_int = _ini[“rtsp”].toInt(“port”);

    // string转double：若值无法转换为double，返回0.0
    double 键值_double = _ini[“段名”].toDouble(“键名”);
    // 示例：double pi = _ini[“math”].toDouble(“PI”);`

    • 补充：检查键是否存在（避免读取不存在的键抛出异常）：

    if (_ini[“rtsp”].isKeyExist(“port”)) {

    3.3.3 重要使用说明（补充常见问题和解决方法）

    使用inicpp库时，需严格遵循以下规则，避免出现编译报错、读写异常等问题，补充实操中常见的问题及解决方法：

    • 中文支持：该库完全支持中文，包括段名、键名、值和注释，无需额外配置编码；推荐使用UTF-8编码保存INI文件和C++代码，避免中文乱码（Windows平台默认GBK编码，需转换为UTF-8）。

    • 注释规则：注释必须为单独的一行，不可与键值对在同一行；若注释与键值同列，写入操作会自动删除该注释；注释支持#和;开头，inicpp库均可解析。

    • 类型规则：读写参数值时，inicpp库仅支持string类型，不可直接使用QString类型（Qt项目需手动转换为std::string），否则会编译报错；转换时使用toLocal8Bit()，避免中文乱码。

    • 段的规则：读写参数前，建议先检查对应的段是否存在（可通过isKeyExist间接判断，或先创建段）；首次创建段后，重启程序再读写该段下的键值对，不会出现异常；若段不存在直接读写键值，会抛出异常（可通过try-catch捕获）。

    • 编译配置：需确保项目编译标准为C++11及以上（添加编译参数-std=c++11）；若包含inicpp.hpp后编译报错，需在该头文件中添加#include （解决部分编译器兼容问题）；若提示“未定义标识符inicpp”，需检查头文件路径是否正确，是否包含inicpp.hpp。

    • 常见问题解决：

      • 问题1：编译报错“error: ‘array’ is not a member of ‘std’” → 解决：在inicpp.hpp头文件顶部添加#include 。

      • 问题2：中文乱码 → 解决：INI文件和C++代码均保存为UTF-8编码，Qt项目转换路径时使用toLocal8Bit()。

      • 问题3：读取不存在的键抛出异常 → 解决：读取前用isKeyExist判断，或用try-catch捕获异常。

      • 问题4：写入后注释丢失 → 解决：确保注释为单独一行，不与键值同列，避免使用modify函数覆盖注释。
